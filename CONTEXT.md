# ElectronicLive Domain Glossary & Architecture Context

This document defines the core domain concepts, entities, and architectural terminology across the ElectronicLive system.

---

## 1. Core Event Search Domain

### `EventResponse`
The canonical, normalized event contract exposed by the .NET Web API and consumed by the React client. Represents a consolidated London live music gig or club night with aggregated ticket offers across all upstream ticketing platforms.
- **Key Attributes:** `Id`, `Name`, `Artists`, `VenueName`, `VenueAddress`, `Date`, `StartDateUtc`, `EndDateUtc`, `Genre`, `Status`, `Offers`, `ImageUrl`.

### `EventTicketOffer`
A normalized ticket purchasing option associated with an `EventResponse`. Encapsulates provider identity, purchase URL, pricing range, and real-time ticketing availability.
- **Key Attributes:** `Provider` (`Ticketmaster`, `Skiddle`, `ResidentAdvisor`), `Url`, `PriceMin`, `PriceMax`, `Currency`, `Status` (`OnSale`, `SoldOut`, `Postponed`, `Cancelled`, `Unknown`).

### `EventGenres`
The standardized genre taxonomy for classifying London electronic music events. Normalizes disparate vendor genre taxonomies into consistent categories: `Techno`, `House`, `Drum & Bass`, `Trance`, and `Garage`.

### `EventStatus`
The normalized lifecycle and ticket availability status of an event: `OnSale`, `SoldOut`, `Postponed`, `Cancelled`, or `Unknown`.

### `EventProvider`
The enumeration of integrated third-party gig and ticketing data providers:
- `Ticketmaster`: Queried via REST Discovery API v2.
- `Skiddle`: Queried via REST Events API.
- `ResidentAdvisor`: Queried via GraphQL endpoint.

### `IEventSearchService` / `EventSearchService`
The primary domain orchestration service for live event discovery. Executes non-blocking concurrent queries (`Task.WhenAll`) across all registered `IEventProvider` implementations with Polly resilience pipelines, deduplicates cross-platform results, and manages two-tier `HybridCache` response caching with hybrid date slicing (in-memory date slicing for artist/genre queries, upstream date bounding for broad date-only discovery).

### `DateRangeFilter`
The date boundary filter encapsulating optional `from` and `to` ISO dates (`DateOnly`). When an artist or genre is specified, the full tour schedule is cached and sliced in memory; when searching by date alone without keywords, the window is capped at 7 days and forwarded upstream to Ticketmaster and Skiddle to protect upstream capacity. Dateless events are excluded when an active date range is applied.

### `EventDeduplicator`
The algorithmic deduplication engine that groups multi-platform listings by composite date and normalized venue keys (`yyyy-MM-dd_{normalizedVenue}`), merging duplicate listings into a single `EventResponse` with unified ticket offers while preserving vendor-specific links and pricing.

### `IArtistVerificationService`
A cross-provider domain capability that verifies whether a requested artist string corresponds to an authentic, recognized music artist across upstream ticketing directories before permitting new subscription creation.

## 2. Artist Watchlist & Notification Domain

### `User`
The persisted domain entity representing a subscriber in the system. Identified by a normalized, lowercase email address and provisioned with a secure, cryptographically random `UnsubscribeToken` used for one-click tokenized unsubscribe operations.

### `Subscription`
The relational domain entity linking a `User` to a specific tracked artist within a designated city (default: `London`). Tracks subscription state via an `IsActive` boolean flag, enabling idempotent subscription activation, deactivation, and reactivation without losing historical notification logs.

### `NotificationLog`
The audit and deduplication entity that records every event notification successfully sent for a given `Subscription`. Stores the deterministic `EventFingerprint` and UTC dispatch timestamp to guarantee users never receive duplicate email alerts for the same event across subsequent scanner runs.

### `EventFingerprint`
A deterministic composite string key formatted as:
`{yyyy-MM-dd}_{normalizedVenue}_{normalizedArtist}`
Generated by `WatchlistScannerService` to uniquely identify an artist's appearance at a specific venue on a specific date, providing idempotent tracking across recurring scan executions.

### `IWatchlistScannerService` / `WatchlistScannerService`
The background batch processing engine executed on a recurring cron schedule by the Azure Container Apps Job runner (`0 8,18 * * *`). It performs the following orchestration lifecycle:
1. Queries distinct monitored artists across all active subscriptions to minimize upstream provider API calls.
2. Fetches upcoming London events for each artist via `IEventSearchService`.
3. Compares discovered events against existing `NotificationLog` records per subscriber using `EventFingerprint`.
4. Renders responsive HTML email digests for subscribers with new/unnotified events.
5. Dispatches emails via `IEmailDispatcher` and records newly sent fingerprints in `NotificationLog`.

### `IEmailDispatcher`
The domain abstraction for email delivery. Decouples notification orchestration from concrete transport providers:
- `ResendEmailDispatcher`: Production implementation that transmits transactional HTML emails via the Resend REST API.
- `LoggingEmailDispatcher`: Development and offline implementation that logs dispatch telemetry to `ILogger` and writes fully rendered `.html` preview files to `.scratch/emails/` for local inspection.

### `EmailTemplateBuilder`
The embedded HTML template rendering engine. Loads the production-ready email template from compiled assembly embedded resources (`Templates/DigestTemplate.html`) and hydrates it with artist details, responsive dark-mode event cards, multi-provider ticket buttons, and secure unsubscribe links.

### `ISubscriptionService` / `SubscriptionService`
The domain service managing subscription lifecycle and intake. Handles user upsertion, artist verification validation, subscription creation/reactivation (`SubscribeOutcome`), and tokenized unsubscribe processing (`UnsubscribeOutcome`).

### `SubscribeOutcome` & `UnsubscribeOutcome`
Pragmatic domain result types describing the exact outcome of subscription operations (e.g., `Created`, `Reactivated`, `AlreadyActive`, `ArtistNotFound`, `ValidationFailed` for subscriptions; `Success`, `AlreadyUnsubscribed`, `InvalidToken` for unsubscriptions).
